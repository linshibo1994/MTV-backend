# 全系统真实验收与缺陷修复 Spec

> 日期：2026-07-18  
> 代码基线：`b6c1e17`  
> 执行分支：`codex/full-system-validation`

## 1. 目标

依据 `docs/` 的原始需求，对当前仓库可交付的后端执行一次可重复、可追溯的全量真实验收。覆盖 T0-T10、全部 FastAPI 路由、权限与错误契约、积分和异步状态机、端到端制作流程、数据库迁移、Redis/Celery、媒体存储与已配置的真实 AI Provider。发现确定性缺陷后，先形成失败证据，再按根因修复并回归。

## 2. 需求与证据基线

采用以下优先级解决文档冲突：

1. `docs/Claude/07-研究方法与证据等级.md` 定义事实等级。
2. `01`、`05`、`04`、`03`、`02`、`06` 分别约束产品、主流程、数据/API、架构、交互和 AI 契约。
3. `08` 是复刻系统的权限、状态机与 Given-When-Then 验收基线。
4. `09` 是探索覆盖清单；标记为待验证且没有产品契约的项目不得冒充已确认需求。
5. `docs/superpowers/` 和 `BACKEND-*` 是后续修复设计与历史执行记录，只能作为实现线索，不能替代本轮新鲜验证证据。

## 3. 范围

- T0：配置安全、应用装配、OpenAPI、错误体、数据库、迁移、Redis、Celery、锁文件。
- T1：登录、登出、会话、组织切换、个人/团队项目权限、成员管理与 IDOR 防护。
- T2：账户、日志、下发、reserve/settle/release/refund、幂等、并发与失败回滚。
- T3：剧本/分集生命周期、版本冲突、五阶段流水线、手动重提取和失败重试。
- T4：主体、父主体、候选、审核、人工锁、差异建议、替换影响与资产条目。
- T5：Materials、Canvas、delta、节点/边完整性、图片元数据与持久化。
- T6：单个/批量生图、取消、幂等、Provider、少图结算、存储和候选联动。
- T7：分镜生成/轮询/编辑/取消/重试、层级、工作台、封面与输入版本栅栏。
- T8：单个/批量视频、素材检查、Provider、取消、首尾帧、多参考图和积分一致性。
- T9：时间线 CRUD、重排、render/status/cancel/retry、trim、持久化与成片存储。
- T10：上传、真实 MIME、鉴权代理、Range、本地存储路径安全、对象晋升与删除清理。
- 横向：统一错误契约、审计、任务 outbox、并发/幂等、租户隔离和完整端到端流程。

### 3.2 仓库边界

当前仓库只有 `backend/` 与需求文档，没有可运行前端。页面视觉、浏览器事件、防抖、未保存离开拦截、Toast、响应式和 a11y 不得宣称已测试；本轮验证这些交互所依赖的 HTTP 契约、权限、状态流转和数据持久化。文档明确排除的新闻播报实功能、实时协同、移动端、自助注册、TTS、字幕、特效/转场和多语言仍不扩入本任务。

## 4. 真实测试分层

1. **静态与确定性层**：全量 pytest、Ruff、Mypy、compileall、`uv lock --check`、OpenAPI 唯一性和路由覆盖。
2. **真实基础设施层**：在任务专用数据库/容器或隔离数据库中执行 PostgreSQL 16 迁移往返、约束和并发测试；真实 Redis 投递与 Celery worker 消费；真实本地存储读写/Range/删除；可用时验证 ffmpeg/ffprobe。
3. **真实 HTTP 层**：启动本轮专用 Uvicorn 端口，使用迁移创建的 PostgreSQL 数据库和真实 Cookie 会话；逐路由验证可达性，并贯通登录、项目、分集、流水线、资产、画布、分镜、视频、时间线和媒体流程。测试数据必须带任务前缀并清理。
4. **真实 Provider 层**：应用运行时加载 `.env`，不得读取或打印密钥。对当前已配置的百炼文本/对话/图片与火山视频执行最小必要请求；验证结构化契约、下载、存储与清理。未配置厂商通过 mock/协议测试验证路由、请求组装、轮询、错误和安全边界，不发起无凭据外呼。

## 5. 外部副作用与资源约束

- 真实 AI 外呼可能计费，只执行能证明能力和业务契约的最小样本；同一能力成功后不重复消耗性调用。
- 不回显请求头、Cookie、令牌、密钥或完整 Provider 原始响应；日志只记录厂商、模型、状态、耗时、产物类型/大小和清理结果。
- 不清空或迁移用户现有数据库；优先使用本任务创建的隔离数据库或容器。
- 记录本轮启动的命令、容器、PID、端口和对象 key；结束时停止并确认释放。本轮未启动的既有资源不得停止。
- 真实外部产物必须在验证后删除；若删除失败，报告精确的非敏感对象标识与风险。

## 6. 缺陷处理工作流

每个缺陷必须依次满足：

1. 稳定复现并保留错误、输入和组件边界证据。
2. 对照同仓库可工作实现，定位根因并提出单一可证伪假设。
3. 先增加最小失败测试或可重复脚本，再实施单一根因修复。
4. 运行专项测试和受影响模块回归。
5. 独立规格复核确认没有漏项或扩项。
6. 独立代码质量复核修复 Critical/Important 问题。

共享文件或同一职责的写入串行进行；互不重叠的调查、验证和修复可并行。

## 7. 完成标准

- 需求到接口/流程/测试的矩阵完整，所有当前注册路由均有本轮证据。
- 全量测试、Ruff、Mypy、compileall、锁文件与 OpenAPI 检查通过。
- PostgreSQL 迁移/约束、Redis/Celery、真实 HTTP、存储和当前已配置 Provider 均有新鲜结果。
- 核心业务流程达到成功终态，同时覆盖权限拒绝、错误契约、冲突、幂等、取消和失败补偿。
- 所有已发现的仓库内确定性缺陷均修复并经双重评审；外部或环境阻塞明确列出证据和剩余风险。
- 本轮服务、端口、容器、临时数据和媒体对象全部清理；差异不含密钥、`.env` 或无关改动。
- 生成最终验收记录，使用中文提交信息提交本任务文件，不推送远端。
