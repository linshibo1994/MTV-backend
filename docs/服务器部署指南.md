# MTV 后端服务器部署指南

> 适用范围：本仓库当前的 `backend/`（FastAPI、PostgreSQL、Redis、Celery、Alembic、FFmpeg 与 AI/对象存储适配层）。
>
> 本文依据仓库当前代码和配置编写，目标环境为 Ubuntu 24.04 LTS 单机或应用节点。前端工程不在本仓库中，因此前端的构建与静态文件发布不在本文范围内。

## 1. 先读：部署结论与推荐路径

推荐先采用 **主机进程 + systemd + Nginx + 托管 PostgreSQL/Redis/S3** 的方式上线。它与当前仓库的运行方式完全匹配，且 API、Celery worker 与 beat 可以共享一个确定的运行目录。

```text
浏览器 / 前端
       │ HTTPS :443
       ▼
     Nginx（同域反代 /v3api 与媒体代理）
       │ HTTP 127.0.0.1:8000
       ▼
 FastAPI（mtv-api.service） ─────── PostgreSQL 16+
       │                              Redis 7+
       ├──────── Redis DB 0（应用缓存）
       ├──────── Redis DB 1（Celery broker）
       └──────── Redis DB 2（Celery result backend）
       │
       ├──── Celery worker（mtv-worker.service）── FFmpeg、对象存储、AI 服务
       └──── Celery beat（mtv-beat.service，必须仅一实例）
```

当前仓库中的 `backend/docker-compose.yml` 是**本地开发编排**：它设置 `APP_ENV=dev`、挂载整个源码目录，只启动 PostgreSQL、Redis、worker 和 beat，且没有 API 服务。`backend/Dockerfile` 也只安装依赖，并未把应用源码 `COPY` 进镜像。因此不要直接把现有 Compose 文件当成生产编排使用；详见 [第 13 节](#13-容器化现状与生产化改造清单)。

当前工作区存在尚未提交的应用与迁移改动。部署时必须选择已审查、已提交并有明确 tag/commit 的版本；尤其不能把未提交的 Alembic revision 当作已发布迁移。

## 2. 代码审计得到的运行约束

| 范围 | 代码事实 | 部署含义 |
|---|---|---|
| HTTP 服务 | 应用入口是 `app.main:app`，文档和 OpenAPI 位于 `/v3api/docs`、`/v3api/openapi.json` | Nginx 需把 `/v3api/` 原样转发，Uvicorn 只监听本机回环地址 |
| 存活检查 | `GET /v3api/health` 返回 `status` 与当前环境名 | 可作为 API 存活探针；它不探测 PostgreSQL、Redis、对象存储或 AI 服务 |
| 数据库 | SQLAlchemy 使用 asyncpg；Alembic 从 `DATABASE_URL` 读取同一异步 URL | 生产数据库 URL 必须使用 `postgresql+asyncpg://`；迁移前先备份 |
| 后台任务 | worker 必须导入 pipeline、生成、分镜、视频、时间线、媒体存储等任务；beat 每 5–60 秒调度补偿和清理任务 | API、worker、beat 都必须常驻；beat 只能运行一个实例，避免重复调度 |
| 媒体处理 | 视频生成和时间线合成都调用 `ffmpeg`（时间线支持 `FFMPEG_BIN`） | API/worker 所在系统都安装 FFmpeg；若本地存储，API 与 worker 必须看见同一个存储目录 |
| 存储 | 默认 local；也支持 S3 兼容存储，S3 模式依赖可选包 `boto3` | 生产优先 S3；若保留 local，不能横向扩容到多台机器 |
| 会话与 CORS | 生产环境强制高强度 `SESSION_SECRET`；会话 Cookie 自动设置 `Secure`；CORS 禁止 `*` | 必须设 `APP_ENV=prod`、可信前端 Origin 的 JSON 数组和 32 字符以上随机密钥 |
| AI 配置 | 文本、对话、图片、视频分别由环境变量选择 provider，启动时读取一次 | 修改任一模型或密钥后，API、worker、beat 都要重启 |

仓库来源：`backend/app/main.py`、`backend/app/api/router.py`、`backend/app/core/config.py`、`backend/app/core/database.py`、`backend/app/workers/celery_app.py`、`backend/app/workers/timeline_render.py`。

## 3. 上线前决策与验收标准

在登录服务器前确认以下选择，避免运行时临时切换造成数据或费用风险：

1. 域名与 TLS：例如 `api.example.com`，或把 API 与 SPA 放在同一域名；同域是最简单可靠的会话方案。
2. 数据库：推荐托管 PostgreSQL 16+；单机可自建 PostgreSQL。数据库、Redis 均不得暴露至公网。
3. 媒体存储：推荐 S3 兼容对象存储；仅单机试运行才使用本地目录。
4. AI 厂商：每项能力只选一个已确认有配额的 Provider，配置最低权限 API Key，并设置预算/告警。
5. 容量：视频渲染与视频生成任务单次硬超时为 900 秒；工作进程、磁盘临时空间和带宽需按该类任务预留。

上线验收至少应同时满足：

- `GET /v3api/health` 返回 200；
- Alembic 当前版本为 `head`；
- PostgreSQL、Redis、API、worker、beat 均为健康状态；
- 能完成一个受鉴权的上传/读取或生成链路的预发布验证；
- API、worker、beat 的有效配置一致；
- Nginx 已启用 HTTPS，安全组只开放 SSH 管理端口与 80/443；
- 已完成上线前数据库与媒体存储备份。

## 4. 服务器前置条件

### 4.1 建议规格

| 场景 | 起步规格 | 说明 |
|---|---:|---|
| 联调/小流量 | 4 vCPU、8 GiB RAM、80 GiB SSD | worker 并发从 2 起步；本地媒体会额外占空间 |
| 有视频合成 | 8 vCPU、16 GiB RAM、200 GiB SSD 或以上 | FFmpeg 临时文件、上传与下载会放大磁盘和 I/O 压力 |
| 多实例/生产 | 应用节点无状态化 + 托管 PG/Redis/S3 | 本地存储不能跨节点共享，需切换到 S3 |

应用对外只需要 80/443；8000、5432、6379 必须限制为本机或私网。系统时间应启用 NTP；所有服务以 UTC 写入任务时间，日志系统可按本地时区展示。

### 4.2 安装系统包与运行用户

以下命令以 Ubuntu 24.04 为例。请先以具有 sudo 权限的管理员账号登录，再创建专用运行用户：

```bash
sudo apt-get update
sudo apt-get install -y \
  git curl ca-certificates build-essential \
  python3.12 python3.12-venv python3-pip \
  ffmpeg nginx postgresql-client redis-tools

sudo adduser --system --group --home /srv/mtv mtv
sudo install -d -o mtv -g mtv -m 0750 /srv/mtv /var/lib/mtv /var/log/mtv
```

验证媒体能力依赖：

```bash
ffmpeg -version
ffprobe -version
```

安装 `uv` 时优先采用组织的受管制软件源；若无该限制，可按 uv 官方安装方式安装。确认 `uv --version` 可在 `mtv` 用户的非交互 shell 中运行。不要在生产服务器使用开发环境的 `--reload`。

## 5. 获取代码与安装锁定依赖

以下示例将发布版本固定到 Git tag 或经过审核的 commit，而不是直接部署漂移的分支头：

```bash
sudo -u mtv -H git clone <你的仓库地址> /srv/mtv/app
sudo -u mtv -H git -C /srv/mtv/app checkout <发布-tag或commit>

cd /srv/mtv/app/backend
sudo -u mtv -H uv sync --frozen --no-dev
```

若使用 S3/MinIO/COS/AWS S3 存储，安装可选依赖后再启动服务：

```bash
cd /srv/mtv/app/backend
sudo -u mtv -H uv sync --frozen --no-dev --extra s3
```

`uv.lock` 已在仓库中锁定，生产环境应使用 `--frozen`；不要在服务器上不受控地升级依赖。验证关键二进制：

```bash
cd /srv/mtv/app/backend
sudo -u mtv -H .venv/bin/python --version
sudo -u mtv -H .venv/bin/uvicorn --version
sudo -u mtv -H .venv/bin/celery --version
```

## 6. 生产环境变量

### 6.1 配置文件位置与权限

不要在仓库中创建或提交真实 `.env`，也不要把密钥放在 systemd unit 文件中。建议使用仅运行用户可读的 `/etc/mtv/backend.env`：

```bash
sudo install -d -o root -g mtv -m 0750 /etc/mtv
sudo install -o root -g mtv -m 0640 /dev/null /etc/mtv/backend.env
sudoedit /etc/mtv/backend.env
```

`Settings` 同时支持环境变量和工作目录 `.env`，但 systemd 的 `EnvironmentFile` 更适合生产权限管理。三个服务将读取**同一个**文件，禁止只更新其中一个服务的配置。

### 6.2 最小生产模板

以下内容只使用占位值，请替换后再保存。URL 中出现 `#`、空格或特殊字符时，优先使用 URL 编码的密码；不要把密码原文写入命令历史。

```dotenv
# 应用与浏览器安全
APP_ENV=prod
APP_HOST=127.0.0.1
APP_PORT=8000
SESSION_SECRET=<用密码管理器生成的随机字符串，至少32字符>
SESSION_COOKIE_NAME=flowapp_session
SESSION_MAX_AGE=86400
# 必须为 JSON 数组，不能写通配符 *；同域前端可写实际 HTTPS 域名
CORS_ORIGINS=["https://app.example.com"]

# PostgreSQL：两条 URL 都指向同一库，驱动名不可互换
DATABASE_URL=postgresql+asyncpg://<app_user>:<url编码密码>@<pg-host>:5432/<db_name>
DATABASE_SYNC_URL=postgresql+psycopg2://<app_user>:<url编码密码>@<pg-host>:5432/<db_name>

# Redis：0 为应用、1 为 broker、2 为 result backend；生产 Redis 要求认证与私网访问
REDIS_URL=redis://:<redis密码>@<redis-host>:6379/0
CELERY_BROKER_URL=redis://:<redis密码>@<redis-host>:6379/1
CELERY_RESULT_BACKEND=redis://:<redis密码>@<redis-host>:6379/2

# 推荐：生产对象存储
STORAGE_DRIVER=s3
S3_ENDPOINT=https://<你的S3兼容端点>
S3_ACCESS_KEY=<对象存储访问密钥>
S3_SECRET_KEY=<对象存储密钥>
S3_BUCKET=<已创建的私有桶>
S3_REGION=<区域，例如us-east-1>

# 按实际模型厂商填写，所有服务保持完全一致
TEXT_LLM_PROVIDER=<openai|deepseek|bailian|anthropic|gemini|openai_compatible>
TEXT_LLM_API_KEY=<文本模型密钥>
TEXT_LLM_MODEL=<文本模型名>
CHAT_LLM_PROVIDER=<同上或另选>
CHAT_LLM_API_KEY=<对话模型密钥>
CHAT_LLM_MODEL=<对话模型名>
IMAGE_GEN_PROVIDER=<openai|gemini|bailian>
IMAGE_GEN_API_KEY=<图像模型密钥>
IMAGE_GEN_MODEL=<图像模型名>
VIDEO_PROVIDER_SELECTION_MODE=env
VIDEO_GEN_PROVIDER=<volcengine|bailian|openai|gemini>
VIDEO_GEN_API_KEY=<视频模型密钥>
VIDEO_GEN_MODEL=<视频模型名>
```

在真正启用视频参考图审核时，火山视频路径还需要独立的 `VOLC_IMAGEX_ACCESS_KEY`、`VOLC_IMAGEX_SECRET_KEY`、`VOLC_IMAGEX_SERVICE_ID`。它们**不能**复用 `VOLCENGINE_API_KEY`；审核服务只能读取可公开安全访问的 HTTPS 预签名对象 URL。若不使用该能力，先依据业务要求显式评估 `VOLC_IMAGE_AUDIT_ENABLED`，不要仅因“方便上线”而关闭审核。

### 6.3 配置项分组说明

| 配置组 | 必填条件 | 关键规则 |
|---|---|---|
| `APP_ENV`、`SESSION_SECRET`、`CORS_ORIGINS` | 所有生产环境 | `APP_ENV=prod` 才会启用 Secure 会话 Cookie 和密钥强度校验；CORS 必须是精确 origin JSON 数组 |
| `DATABASE_URL`、`DATABASE_SYNC_URL` | 必填 | 前者使用 `asyncpg`，后者使用 `psycopg2`；迁移实际从前者读取 |
| 三个 Redis URL | 必填 | 保持数据库号 0/1/2 隔离；建议 TLS/认证/私网，按 Redis 服务能力使用 `rediss://` |
| `STORAGE_*` | 必填 | S3 模式需 `boto3` 额外依赖和访问桶的读写删权限；local 模式需共享绝对路径 |
| `TEXT_LLM_*`、`CHAT_LLM_*` | 启用剧本流水线或对话时 | 可设置专属 `*_BASE_URL`；生产环境带 API Key 的远端地址必须是 HTTPS |
| `IMAGE_GEN_*` | 启用图片生成时 | Provider 和模型必须匹配；空值可能回退至旧厂商字段 |
| `VIDEO_GEN_*` | 启用视频生成时 | 新部署建议设 `VIDEO_PROVIDER_SELECTION_MODE=env`，避免旧数据库动态配置覆盖环境选择 |
| `DASHSCOPE_*`、`ANTHROPIC_*`、`DEEPSEEK_*`、`GEMINI_*`、`VOLCENGINE_*` | 使用相应 Provider 且未用统一能力变量时 | 统一能力变量为空时会按 Provider 回退到这些兼容字段 |
| `MAX_UPLOAD_BYTES`、`MAX_MEDIA_READ_BYTES` | 按容量调整 | 默认分别为 512 MiB 与 2 GiB；变更前核对 Nginx 请求体上限与可用磁盘 |
| `PIPELINE_EXTRACT_CONCURRENCY`、`PIPELINE_ENRICH_CONCURRENCY` | 按供应商配额调整 | 代码限制为 1–16；这不是 Celery 进程并发数 |
| `EDITOR_CAN_REVIEW` | 可选 | 默认为 `false`；这是权限策略，不应作为部署时的随意开关 |

模型厂商的完整组合、回退规则和限制见 [PROVIDERS.md](./PROVIDERS.md)。每次修改配置后都需重启 API、worker、beat，因为配置在导入时缓存为单例。

### 6.4 使用本地媒体目录的例外

若仅单机部署且暂不使用对象存储：

```dotenv
STORAGE_DRIVER=local
STORAGE_ROOT=/var/lib/mtv/storage
```

随后创建目录并赋权：

```bash
sudo install -d -o mtv -g mtv -m 0750 /var/lib/mtv/storage
```

API 与 worker 必须使用完全相同的绝对路径。该模式不适用于多机负载均衡或滚动发布到多个节点；本地磁盘损坏也会直接导致媒体丢失，因此必须纳入快照/异地备份。

## 7. 初始化 PostgreSQL、Redis 与迁移

### 7.1 PostgreSQL

建议由 DBA 或托管服务控制平面创建数据库和最小权限应用账号。以下仅为自建 PostgreSQL 的示例：

```sql
CREATE ROLE mtv_app LOGIN PASSWORD '<强密码>';
CREATE DATABASE mtv OWNER mtv_app ENCODING 'UTF8';
REVOKE ALL ON DATABASE mtv FROM PUBLIC;
```

允许应用账号在目标库中执行 Alembic 迁移，或在发布窗口使用单独的迁移账号。禁止把超级用户凭据放入 API/worker 的常驻环境文件。

在第一次启动常驻进程前，先执行迁移。生产迁移是写操作，请先完成备份并在单个发布节点串行运行。为避免从 shell 解析或回显密钥，使用 [第 8.4 节](#84-迁移-unit-etc-systemdsystemmtv-migrateservice) 的一次性 systemd service 执行，而不是在终端拼接环境变量。

### 7.2 Redis

Redis 是任务 broker/result backend，也是应用缓存依赖。至少做到：

- 仅监听回环地址或私有网络；禁止 6379 对公网开放；
- 启用认证，托管 Redis 则启用 TLS；
- 使用持久化与监控策略，容量不足会阻塞任务调度；
- 不与其他系统混用数据库 1/2，避免清理策略误删 Celery 数据；
- 部署前分别验证三个 URL 对应的认证和网络连通性。

## 8. 使用 systemd 常驻运行

以下 unit 以 `/srv/mtv/app/backend` 为工作目录，确保相对路径、Alembic 和媒体临时行为一致。先以 root 写入，再执行 `daemon-reload`。

### 8.1 API：`/etc/systemd/system/mtv-api.service`

```ini
[Unit]
Description=MTV FastAPI API
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=mtv
Group=mtv
WorkingDirectory=/srv/mtv/app/backend
EnvironmentFile=/etc/mtv/backend.env
Environment=PYTHONUNBUFFERED=1
ExecStart=/srv/mtv/app/backend/.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000 --proxy-headers --forwarded-allow-ips=127.0.0.1
Restart=always
RestartSec=5
TimeoutStopSec=30
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=full
ReadWritePaths=/var/lib/mtv /var/log/mtv

[Install]
WantedBy=multi-user.target
```

当前数据库连接池固定为 `pool_size=10`、`max_overflow=20`。在单机起步阶段先只运行一个 Uvicorn 进程；若增加 Uvicorn worker 或 API 实例，需按“实例数 × 最大连接数”核对 PostgreSQL 的连接上限并设置连接池预留。

### 8.2 Celery worker：`/etc/systemd/system/mtv-worker.service`

```ini
[Unit]
Description=MTV Celery Worker
After=network-online.target mtv-api.service
Wants=network-online.target

[Service]
Type=simple
User=mtv
Group=mtv
WorkingDirectory=/srv/mtv/app/backend
EnvironmentFile=/etc/mtv/backend.env
Environment=PYTHONUNBUFFERED=1
ExecStart=/srv/mtv/app/backend/.venv/bin/celery -A app.workers.celery_app worker -l INFO --concurrency=2 --max-tasks-per-child=100
Restart=always
RestartSec=5
# 任务硬超时为 900 秒，给 warm shutdown 留出余量
TimeoutStopSec=930
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=full
ReadWritePaths=/var/lib/mtv /var/log/mtv

[Install]
WantedBy=multi-user.target
```

`--concurrency=2` 只是保守起点：视频渲染为 CPU/磁盘密集，外部生成任务又受供应商配额约束。基于 CPU、RAM、FFmpeg 负载、AI 限流和队列延迟逐步调高；不要把 `PIPELINE_*_CONCURRENCY` 与此参数混为一谈。

### 8.3 Celery beat：`/etc/systemd/system/mtv-beat.service`

```ini
[Unit]
Description=MTV Celery Beat Scheduler
After=network-online.target mtv-worker.service
Wants=network-online.target

[Service]
Type=simple
User=mtv
Group=mtv
WorkingDirectory=/srv/mtv/app/backend
EnvironmentFile=/etc/mtv/backend.env
Environment=PYTHONUNBUFFERED=1
ExecStart=/srv/mtv/app/backend/.venv/bin/celery -A app.workers.celery_app beat -l INFO --schedule /var/lib/mtv/celerybeat-schedule
Restart=always
RestartSec=5
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=full
ReadWritePaths=/var/lib/mtv /var/log/mtv

[Install]
WantedBy=multi-user.target
```

**只允许一个 beat 实例**。代码中的 outbox 派发、过期任务恢复、积分清理、视频取消补偿、媒体存储恢复等都依赖 beat；运行多个实例会重复投递周期任务。

### 8.4 迁移 unit：`/etc/systemd/system/mtv-migrate.service`

```ini
[Unit]
Description=MTV Alembic Migration (oneshot)
After=network-online.target
Wants=network-online.target

[Service]
Type=oneshot
User=mtv
Group=mtv
WorkingDirectory=/srv/mtv/app/backend
EnvironmentFile=/etc/mtv/backend.env
ExecStart=/srv/mtv/app/backend/.venv/bin/alembic upgrade head
```

启用并启动服务：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now mtv-api mtv-worker mtv-beat

sudo systemctl status mtv-api mtv-worker mtv-beat --no-pager
sudo journalctl -u mtv-api -u mtv-worker -u mtv-beat -n 200 --no-pager
```

首次发布与每次含 migration 的发布，都先执行并核对：

```bash
sudo systemctl start mtv-migrate.service
sudo systemctl status mtv-migrate.service --no-pager
```

## 9. Nginx 与 HTTPS

以下示例假定 API 走 `api.example.com`。若 SPA 与 API 同域，前端请求 `/v3api/...` 即可，通常不需额外 CORS；若使用独立前端域名，则把它加入 `CORS_ORIGINS`。

`/etc/nginx/sites-available/mtv-api`：

```nginx
server {
    listen 80;
    server_name api.example.com;
    client_max_body_size 512m;

    # 证书签发前临时保留；签发后应重定向到 HTTPS。
    location / {
        return 301 https://$host$request_uri;
    }
}

server {
    listen 443 ssl http2;
    server_name api.example.com;
    client_max_body_size 512m;

    ssl_certificate     /etc/letsencrypt/live/api.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.example.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;

    # 视频上传与合成可能耗时较长；按业务和上游网关限制调整。
    proxy_connect_timeout 30s;
    proxy_send_timeout 930s;
    proxy_read_timeout 930s;

    location /v3api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # 必须保留应用当前的媒体代理前缀；不要把本地 storage 目录直接暴露为静态目录。
    location /api/x/cctv/zhihui/flow-app/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

```

检查并加载：

```bash
sudo ln -s /etc/nginx/sites-available/mtv-api /etc/nginx/sites-enabled/mtv-api
sudo nginx -t
sudo systemctl reload nginx
```

Nginx 的 `client_max_body_size` 必须不小于应用的 `MAX_UPLOAD_BYTES`，否则请求会先被 Nginx 以 413 拒绝。对象存储桶保持私有：应用已实现受控媒体代理和 S3 预签名 URL，禁止为了“方便预览”直接公开桶或映射本地媒体目录。

当前应用默认公开 `/v3api/docs` 与 `/v3api/openapi.json`。若生产安全策略不允许公开接口文档，请在 Nginx 单独限制这两个路径（例如仅放行办公网/VPN），或在应用代码中关闭它们；不要误以为它们已默认受鉴权保护。

## 11. 日常运维

### 11.1 日志与状态

```bash
sudo systemctl status mtv-api mtv-worker mtv-beat --no-pager
sudo journalctl -fu mtv-api
sudo journalctl -fu mtv-worker
sudo journalctl -fu mtv-beat

sudo -u mtv -H /srv/mtv/app/backend/.venv/bin/celery \
  -A app.workers.celery_app inspect ping
sudo -u mtv -H /srv/mtv/app/backend/.venv/bin/celery \
  -A app.workers.celery_app inspect registered
```

建议把 journald 日志接入集中式日志平台，并至少告警：服务重启次数、worker 离线、任务失败率/排队时长、Redis 内存、PostgreSQL 连接/慢查询、磁盘容量、对象存储错误和 AI Provider 429/5xx。

### 11.2 数据与媒体备份

- PostgreSQL：使用托管服务 PITR，或定期逻辑备份与物理备份；演练恢复，而不是只检查备份文件存在。
- S3：启用版本控制、生命周期和跨区域/跨账户备份策略；最小权限凭据只允许目标桶的必要读写删操作。
- local 存储：备份 `/var/lib/mtv/storage`，且与数据库同一恢复点协调；只恢复数据库不恢复媒体会产生失效引用。
- Redis：它保存队列和结果，重启/故障时任务可能需要补偿；不要把它当作唯一业务真相，数据库中的状态与 beat 补偿任务负责恢复。

### 11.3 安全清单

- 真实 `.env`、证书、数据库密码和 API Key 不提交 Git、不写入 shell 历史、不贴进工单；
- 每个外部服务使用独立凭据并定期轮换；轮换后同时重启 API/worker/beat；
- `APP_ENV=prod`、强 `SESSION_SECRET`、精确 `CORS_ORIGINS` 是上线门槛；
- PostgreSQL、Redis、Uvicorn 都只对内网或 loopback 监听；
- API 仅通过 Nginx 的 HTTPS 暴露，开启服务器安全更新、最小化 sudo 和 SSH 密钥登录；
- 对上传大小、Nginx 超时、可用磁盘、对象存储桶策略和 AI 费用预算进行联合限制；
- 不要在 Nginx 上绕过应用鉴权直接公开媒体文件。

## 12. 发布、回滚与故障排查

### 12.1 标准发布流程

1. 记录当前 commit、运行中的 unit 状态、Alembic 当前 revision，完成数据库和媒体备份。
2. 在 CI 或隔离环境运行与改动相关的测试、Ruff、Mypy；生产服务器只负责部署已验证产物。
3. 先从 Nginx 摘除后端流量或停止 API，避免旧版本继续接收新任务；然后停止 worker 并等待至多 930 秒让已领取任务优雅结束，最后停止唯一的 beat。
4. 将代码切到目标 tag/commit，执行 `uv sync --frozen --no-dev`（S3 模式加 `--extra s3`）。
5. 在单一发布节点运行 `mtv-migrate.service`；如果迁移失败，停止并根据备份/迁移策略处理，不要继续启动新版本。
6. 依次启动 worker、beat、API，恢复 Nginx 流量，执行 [第 10 节](#10-首次发布与冒烟验证) 的验证。
7. 观察队列、错误率和资源至少一个业务高峰周期后，再清理上一个发布目录。

建议采用版本目录加 `/srv/mtv/app` 软链接的发布方式，使代码回退可恢复；不要在运行目录里直接 `git pull` 到未知状态。

### 12.2 回滚原则

- **仅代码回滚**：切回上一个已验证的版本，重新安装其 lockfile 依赖，重启三个服务并验证。
- **含数据库迁移的发布**：先确认迁移是否可逆及是否已有新数据写入。Alembic `downgrade` 是数据库写操作，未经演练和备份不可在事故时盲目执行。
- **媒体格式/存储迁移**：数据库、对象与代码必须作为一个恢复单元评估；仅回退代码可能无法读取新格式资产。
- **密钥泄露**：先在 Provider/数据库/对象存储端吊销或轮换，再更新 `/etc/mtv/backend.env` 并滚动重启所有服务。

### 12.3 常见问题

| 现象 | 优先检查 | 处理方向 |
|---|---|---|
| API 无法启动，提示 `SESSION_SECRET` | `journalctl -u mtv-api` 和 `APP_ENV` | 生产密钥至少 32 字符、非默认值且不为低熵重复字符串 |
| API 无法启动，提示 CORS URL 不合法 | `CORS_ORIGINS` | 使用 JSON 数组，写 `https://app.example.com`，不要尾路径、`*`、查询参数或账号信息 |
| API 200 但任务不执行 | `mtv-worker`、Redis DB 1/2、worker `inspect ping` | 恢复 worker 与 Redis 连通性；确认三服务使用同一环境文件 |
| 任务可发起但补偿/清理不运行 | `mtv-beat` 日志与数量 | 确认 beat 正常且仅一实例；不要把 schedule 放在易清理的 `/tmp` |
| 上传返回 413 | Nginx `client_max_body_size` 与 `MAX_UPLOAD_BYTES` | 二者按最小允许上限同时调整，并评估带宽/磁盘风险 |
| 视频合成失败 | `ffmpeg -version`、worker 日志、临时空间 | 安装 FFmpeg，检查 `FFMPEG_BIN`、CPU、磁盘、权限与输入媒体 |
| S3 启动/任务失败 | `STORAGE_DRIVER`、`boto3`、桶权限、endpoint | 用 `uv sync --extra s3` 安装依赖；检查私有桶读写删权限和 Region/Endpoint |
| 跨域登录后仍无会话 | 前端 `credentials: include`、精确 CORS origin、HTTPS | 前端需携带凭据；后端不能配置 `*`；生产 Cookie 必须经 HTTPS |
| 修改 API Key 后仍用旧配置 | 服务重启记录 | 配置在启动时加载；重启 API、worker、beat 三者 |
| worker 停止很久 | 任务硬限时与 systemd 超时 | 任务硬超时为 900 秒；保留足够的 `TimeoutStopSec`，观察 warm shutdown 后再强杀 |

## 13. 容器化现状与生产化改造清单

当前容器资产适用于开发，不应直接上线，原因如下：

| 当前项 | 代码现状 | 生产风险 | 上线前应补齐 |
|---|---|---|---|
| `Dockerfile` | 只复制 `pyproject.toml` 与 `uv.lock` 并安装依赖 | 镜像中没有 `app/` 源码，不能独立运行 | 在构建阶段复制 `app/`、`alembic/`、`alembic.ini`，并以非 root 用户运行 |
| `docker-compose.yml` | 绑定挂载 `.:/app` | 依赖宿主机源码，发布不可复现 | 去除源代码挂载，以不可变镜像和 release tag 部署 |
| Compose 服务 | 只有 PostgreSQL、Redis、worker、beat | 没有 API、Nginx、迁移一次性任务 | 添加 api、迁移 job、健康检查、资源限制和日志策略 |
| 环境 | 明确 `APP_ENV=dev`、开发密钥和对外端口 | 生产 Cookie/安全校验不符合要求，数据服务可能暴露 | 使用外部 secrets/EnvironmentFile，PG/Redis 仅私网暴露 |
| 媒体 | 无生产持久卷/S3 配置 | 容器重建或多副本会丢失/分裂本地媒体 | 生产默认 S3；或将同一持久卷挂到 API 与 worker |
| Celery beat | schedule 写 `/tmp/celerybeat-schedule` | 容器重启会丢失调度状态 | 挂载持久路径，且强制单副本 |

完成以上改造并在预发布环境验证前，本文推荐的 systemd 部署是当前仓库更低风险的上线路径。
